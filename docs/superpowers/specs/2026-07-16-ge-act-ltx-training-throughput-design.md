# GE-Act LTX Training Throughput Design

## Goal

Increase the throughput of the eight-H100 GE-Act LTX + SigLIP2 run while preserving the approved global batch of 128, four future semantic keyframes, two cameras, 256 tokens per keyframe, all-28-block semantic injection, online SigLIP2/VAE/T5 encoding, and gradient checkpointing.

## Approaches considered

1. **Episode-level uint8 NumPy cache (selected).** Decode each camera MP4 once into one atomic `.npy` file per episode and camera. Training reads only the indexed frames through NumPy memory mapping. This removes repeated codec work without changing RGB values or teacher features.
2. **One JPEG/PNG file per frame.** This supports random access but creates hundreds of thousands of small files, stresses the shared filesystem metadata service, and still performs image decompression online.
3. **Offline VAE latents and SigLIP2 features.** This offers the largest speedup, but changes the requested online-conditioning workflow and complicates color augmentation and future feature experiments.

## Selected design

### Cache layout and generation

Add a CPU predecode command that mirrors the source tree below a separate cache root:

```text
<cache-root>/<domain>/videos/<chunk>/<camera>/episode_<id>.npy
```

Each file contains `[T,H,W,3]` RGB `uint8` frames. Generation uses PyAV, writes to a temporary file, validates frame count/shape/dtype, then atomically renames the file. Existing valid files are resumable and skipped. A verification mode compares the expected MP4 set with the cache set and opens every NumPy header before reporting success.

### Dataset integration

`CustomLeRobotDataset` accepts `predecoded_video_root` and `require_predecoded`. When configured, it maps the existing episode/camera path to the cache, clamps requested indices exactly as the MP4 path does, and loads only those frames. With `require_predecoded: true`, a missing or malformed cache raises an explicit error; it never silently falls back to MP4 during the optimized run.

The training configuration retains `source_fps: 20`, `chunk: 9`, `action_chunk: 36`, and `n_previous: 4`, so the effective model rate remains 5 FPS.

### Batch and host configuration

- Per-GPU batch: `8`
- Gradient accumulation: `2`
- GPUs: `8`
- Global batch: `8 * 2 * 8 = 128`
- DataLoader workers: `8` per rank, persistent and prefetched
- Slurm CPUs: `96`
- `OMP_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `NUMEXPR_NUM_THREADS=1`
- Gradient checkpointing remains enabled

If batch 8 fails the short memory smoke test, the only fallback is batch 4 with accumulation 4, preserving global batch 128. Batch 16/accumulation 1 is a later optional experiment, not part of this restart.

### Deployment sequence

1. Stop the current inefficient run after this design is approved.
2. Run the CPU predecode job and require successful full-cache verification.
3. Run local regression tests and the remote preflight.
4. Launch an eight-GPU short runtime check with batch 8/accumulation 2.
5. Continue the 30,000-step job only after the first optimizer steps complete without OOM, NaN, missing-cache fallback, or global-batch mismatch.

The training job continues to save only steps 20,000, 25,000, and 30,000.

## Error handling

- Corrupt or incomplete cache files are regenerated by the predecode command.
- Cache verification fails on missing camera files, empty arrays, non-`uint8` arrays, or wrong frame rank/channel count.
- Runtime cache misses fail immediately with the source and expected cache paths.
- The launcher prints the commit, cache manifest summary, DeepSpeed batch configuration, and GPU inventory into the Slurm log.

## Testing and acceptance

- Unit tests prove cached indexed frames have the same values/order as the decoded source fixture, including repeated and out-of-range indices.
- Unit tests prove strict mode rejects missing cache files.
- Configuration tests prove batch 8, accumulation 2, global batch 128, checkpointing enabled, and strict predecode enabled.
- Preflight verifies cache-root existence and the static training contract.
- Remote acceptance requires all eight GPUs active, approximately stable memory use, no fatal log entries, and measured step time reported against the current 4.84 s/optimizer-step baseline.

The optimization is accepted based on measured throughput, not GPU power alone; H100 power may remain below 700 W for attention-heavy or synchronization-heavy phases.
